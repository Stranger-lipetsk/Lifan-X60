# Вывод: ограничения штатного Android firewall и сетевого ADB

## Короткий ответ

На generic Android 4.4.2 ARM/x86 в одноразовых эмуляторах platform-signed приложение с UID 1000 смогло включить штатный firewall через NetworkManagementService и задать правила для интерфейсов: loopback и собственный адрес гостя блокировались, тогда как входящее TCP-соединение от изолированного host-loopback peer через интерфейс eth0 принималось. Это подтверждает принципиальную возможность разделить IP-доступ по интерфейсам в данном лабораторном образе.

Это НЕ подтверждает, что на головном устройстве это будет работать так же, и НЕ означает, что firewall отключит локальный USB ADB, локальные Unix-domain sockets или другие не-IP transports. Эмуляторный adbd использует qemud; в проведённом тесте его TCP listener не был доступен. Подменять проверку на произвольный TCP listener доказательством реального поведения adbd нельзя.

## Наблюдения

- ARM run `42377911082` завершился успешно: loopback и собственный адрес `10.0.2.15` заблокированы; listener на eth0 принял соединение через одноразовое QEMU host-forward, ограниченный host INPUT firewall для источников loopback; клиент проверил ответ `X60_FW_OK`.
- В том же ARM запуске разрешение loopback было проверено отдельным контрольным шагом, затем firewall отключён и восстановление подтверждено (`FIREWALL_RESTORED_DISABLED=true`).
- Предыдущий x86 run `42375649510` подтвердил loopback/own-address блокировку и host peer roundtrip через QEMU gateway, но не прямой unsolicited входящий TCP.
- На обоих generic образах запись service.adb.tcp.port сама по себе не дала guest TCP listener: ADB использовал эмуляторный qemud transport. Поэтому тесты не проверяли сетевой ADB handshake и доступ root через реальный adbd.
- Правило `setFirewallInterfaceRule` действует на интерфейс целиком в этом сценарии; это не доказательство фильтрации только ADB-порта. Полная блокировка интерфейса lo потенциально затрагивает и прочие локальные IP-соединения.

## Границы применимости

1. Android firewall фильтрует IP-трафик. Он не является механизмом отключения USB/debugging transport, Unix-domain socket или локального shell-доступа.
2. Входящий тест был на синтетическом ServerSocket приложения system UID, не на adbd. QEMU forwarding соединяет host loopback с интерфейсом гостя внутри эмулятора; это не тест через LAN и не эквивалент физического прямого подключения к ГУ.
3. Generic AOSP-derived Android 4.4.2 и stock-derived services.jar не подтверждают, что vendor framework, netd, init, SELinux и firewall на конкретной прошивке совпадают.
4. Никакие настройки firewall на ГУ не применялись; сеть ADB, прошивка и форматирование на ГУ не включались и не выполнялись.

## Дополнительный статический контекст vendor-образа

- В извлечённом `init.rc` property-gated сервис `usbnet_adb` запускает `/system/bin/el_debug_tool` от root только при `persist.sys.usbnet_adb_support=1`; по умолчанию сервис помечен `disabled`. В отдельном `enable_adb.sh` меняется USB config на `mtp,adb`, но это не то же самое, что включение `usbnet_adb`.
- Офлайн-анализ `el_debug_tool` (SHA-256 и дизассемблирование описаны в `reports/usb-debug-static.txt`) обнаружил операции с ASIX-модулем, настройкой `eth0` на `192.168.88.1`, свойством `service.adb.tcp.port=9478` и argv-таблицами для `stop adbd` и `start adbd`. Это показывает предусмотренный vendor-путь USB-Ethernet ADB, но не факт, что он включён или безопасно доступен на текущем ГУ.
- Извлечённая таблица прав init содержит `service.` для UID 1000 и более длинные префиксы `service.adb.root` / `service.adb.tcp.port` для UID 2000. В AOSP 4.4.2 `check_perms()` обходит эту таблицу по порядку, и при совпавшем префиксе с разрешённым UID сразу выполняет SELinux-проверку; общий `service.` стоит раньше двух специальных ADB-префиксов. Если vendor init сохраняет эту логику, UID 1000 может пройти по общему префиксу при разрешающей SELinux policy. Сохранённая policy относит `system_app` к `unconfineddomain` и разрешает property_service set на `shell_prop` (`reports/stock-adb-selinux-static.txt`). Это сильное статическое основание для возможности system-UID приложения менять ADB-свойства, но не runtime-проверка vendor init или конкретного пакета.
- В `system/bin/netd` статически найдена строка `/system/bin/oem-iptables-init.sh` (`reports/sd-boot-update-static.txt`). Сам скрипт в сохранённом извлечении не найден, поэтому нельзя установить, какие vendor-правила он добавляет и перезаписывает ли он правила Android firewall.
- Из ramdisk извлечены `ro.secure=1`, `ro.debuggable=1`, `persist.sys.usb.config=adb`; там же `ro.adb.secure=0` и выключенный по умолчанию root console. Это статические значения образа, не проверка runtime-состояния конкретного ГУ.

Эти находки делают интерфейсное ограничение на `eth0` правдоподобным сценарием для vendor USB-Ethernet ADB: если это действительно выделенный point-to-point USB-Ethernet сегмент, то allow для `eth0`/deny для `lo` концептуально может оставить host-путь и отсечь loopback-путь. Но allow интерфейса не ограничивает доступ до одного IP/порта: любой другой peer, достижимый через `eth0`, тоже попадёт под разрешение. Generic emulator не моделирует custom init/netd путь. Наличие `el_debug_tool` и строки OEM script не подтверждают активные firewall rules, listener или runtime-свойства сервиса.

В предыдущем статическом анализе stock-derived `adbd` в изолированном контейнере зафиксированы root UID при synthetic `service.adb.root=1` и ответ без AUTH при synthetic `ro.adb.secure=0` (`reports/stock-adbd-container-lab.txt`). Это свидетельство риска для такого набора параметров, не доказательство, что vendor USB-Ethernet service запущен, открыт на ГУ или использует эти параметры в runtime.

## Статическая проверка API Android 4.4.2

В AOSP `NetworkManagementService.java` Android 4.4.2_r1 firewall-методы `setFirewallEnabled`, `setFirewallInterfaceRule`, `setFirewallEgressSourceRule`, `setFirewallEgressDestRule` и `setFirewallUidRule` вызывают `enforceSystemUid()`: Binder caller должен иметь ровно `Process.SYSTEM_UID` (1000). Interface rule принимает только имя интерфейса и allow/deny; в этом API нет метода для разрешения только входящего локального destination-port на интерфейсе. Egress-адрес/порт и UID-правила существуют, но не эквивалентны точному входящему фильтру ADB-порта. Ручные iptables-правила теоретически дают более точный контроль, однако их внесение, порядок, персистентность и взаимодействие с OEM netd на прошивке ГУ не установлены.

Источник AOSP для firewall API: https://github.com/aosp-mirror/platform_frameworks_base/blob/android-4.4.2_r1/services/java/com/android/server/NetworkManagementService.java
Источник AOSP для property ACL и порядка `check_perms`: https://github.com/aosp-mirror/platform_system_core/blob/android-4.4.2_r1/init/property_service.c

Исследованный KitKat netd fork создаёт `fw_INPUT`, `fw_OUTPUT` и `fw_FORWARD`; enable добавляет DROP для входящего и REJECT для исходящего/forward, а разрешение интерфейса добавляет `RETURN` для трафика этого интерфейса. В fork доступны также правила источника/адреса/порта и UID, но это не исходники netd прошивки ГУ: https://github.com/Plain-Andy/android_platform_system_netd/blob/kk/FirewallController.cpp

## Итог и модель угроз

Ограничить сетевой IP-доступ loopback/интерфейсными правилами в исследованном generic Android возможно, оставив host-путь через внешний интерфейс. Утверждение «локальный root ADB полностью заблокирован, а прямой ADB с хоста остаётся доступен» остаётся недоказанным: для него нужны сведения о транспорте и политике именно ГУ, а текущий ARM-эмулятор не предоставил реальный TCP adbd endpoint.

Firewall здесь может быть только фильтром того, кто способен открыть сетевое соединение. Если пропущенный клиент получает root ADB, firewall не изолирует его от правил устройства: root потенциально может менять правила/службы. Для ограничения до одного адреса плюс одного входящего порта потребовались бы конкретные vendor/kernel iptables правила и понимание, как их переживают netd restart, смена интерфейса и boot; generic interface allow для этой гарантии недостаточен. USB ADB transport остаётся отдельным путём вне IP firewall.
